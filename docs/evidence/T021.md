## Behavior

`src/lib/server/mistake-cards.ts` generates one editable native note and card
from a confirmed practice mistake. Eligibility is decided on the server from
the stored attempt, session, question, content version and newest evaluation;
the client supplies only the attempt id. A draft exists only when all of these
hold:

- the attempt belongs to the authenticated learner;
- its session is a practice session (assessment answers stay hidden, and
  mixed-review is not a mistake-draft source);
- the newest evaluation is `incorrect` — pending, `uncertain` (including the AI
  fallback's refusal path), correct, `not_sure` and holdout answers create no
  card;
- the content version is not quarantined and the checked prompt/answer exist.

The generated Basic content is Front/Back from the checked prompt and answer.
A Cloze draft is generated only when the prompt contains the `___` blank; it
substitutes the answer into the T003-restricted single-group form
(`{{c1::answer}}`). Other numbered groups, real-client rendering and full Anki
Cloze compatibility are **not** claimed; widening that subset is a T003/T024
decision. The lesson's first paragraph (up to 600 code points, falling back to
the correct answer) is stored as the short explanation, together with the
source attempt, skill and content version.

Drafts live in one deterministic `Mistakes (<language>)` deck per learner and
language. A partial unique index on `(owner_id, source_attempt_id)` permits one
draft per practice attempt, and a repeated request replays the same native note
and card instead of duplicating them.

Editing a draft or an approved note changes `kind`, `content_json` and
`explanation` in place. The note id, generated card id and stable `source_id`
(the Anki note GUID mapping) do not change. Rejecting a note is idempotent and
final: rejected notes cannot be edited or reviewed, and they are excluded from
the due queue. Only explicit approval admits a note to the due queue; approval
is deduplicated. The owner is always derived from the authenticated session,
never from a parameter or body field.

## Surfaces

- `POST /app/api/attempts/[id]/card` creates/replays a draft.
- `GET`/`PATCH /app/api/notes/[id]` reads or edits a note and its card.
- `POST /app/api/notes/[id]/approve` and `POST /app/api/notes/[id]/reject`
  perform the explicit transitions.
- Practice results list confirmed mistakes with a **Keep as flashcard** form;
  the deck page offers edit, approve and reject actions.
- Export remains a user-initiated, one-way, approved-notes-only action. There
  is no delivery queue, background connector or automatic Anki write.

## Test-first evidence

The behavior suite was written before the service existed. The first run was
**RED** with no tests collected:

```text

```

After the additive migration and service implementation, the focused suite
passed 12 tests. One Cloze assertion initially failed because a second draft
request for the same attempt correctly replayed the first draft instead of
re-validating the changed prompt; the test now uses a fresh fixture for the
no-blank case. The final focused suite is **GREEN** with 13 tests, and the
route/page actions (results keep, deck edit/reject) are included.

The final `npm test` run passes 81 files / 1310 tests, including the prior
native-flashcard, review-invariant, migration and owner-scope suites.

## Pending acceptance

- Real Anki client import/re-import and the supported Cloze subset remain T024
  and the T003 manual gate. Synthetic APKG checks do not settle them.
- Broader deck/card management, suspend toggles and tag flows remain T034.
- Content-report rejection has no stored state in the current reporting model;
  reports never create or promote a card, so there is no report-rejection path
  to admit. A report triage workflow would need its own state and tests.
- Production authentication, Turso provisioning and production data ownership
  are not exercised here.
