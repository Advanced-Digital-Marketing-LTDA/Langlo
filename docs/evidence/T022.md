# T022a/T022b: native flashcard identity, scheduling and review integrity

2026-10-19. Rollup evidence for the native flashcard schema, stable
note/card identities, scheduler snapshots and immutable review events. This
replaces the former delivery-queue/AnkiConnect design; there is no outbound
Windows queue. All databases are synthetic disposable fixtures.

The work is based on `origin/main` `c3d10d6`, after the lesson-translations and
Portuguese-explanation PRs merged. It uses migration `0019`, following
`0017_lesson_translations` and `0018_content_change_kinds`; the regenerated
snapshot chains from the `0018` snapshot. Migration `0020` adds trigger-backed
all-or-nothing enforcement for the note source columns, and `0021` requires a
non-null source attempt to match the note owner's skill and content version. Neither merged PR touched the
flashcard service or routes.

## T022a — persisted identities and state

The published migration foundation is extended additively, not replaced:

- `native_flashcard_decks`, `native_flashcard_notes` and `native_flashcards`
  are owner-scoped with composite `(id, owner_id)` keys and owner-bound
  foreign keys. Card ids derive from the note id and ordinal, never from
  mutable prompt text.
- `native_flashcard_review_events` is `WITHOUT ROWID`, keyed by
  `(owner_id, id)`; the id is the idempotency UUID. Events store the selected
  rating, expected revision, server-assigned UTC `reviewed_at`, scheduler
  version, the exact scheduler parameters and the resulting revision/due
  instant. Hand-authored triggers reject UPDATE, DELETE and replacement
  INSERT; the only deletion path is the intentional owner-data cascade.
- Each card stores its own FSRS state, due instant, revision, suspension flag,
  scheduler version and parameters. A review updates that snapshot and
  appends its event in one transaction.
- `source_id` is the stable `langlo:v1:<64 hex>` identity used as the Anki note
  GUID. Editing content, format or explanation does not change it.
- Migration `0019_bizarre_ink` adds `explanation`, `source_skill_id`,
  `source_content_version_id` and `source_attempt_id` to notes, plus the
  partial unique index for one generated draft per practice attempt. It adds
  no table and rewrites no row.
- Learner timezone context remains in `learner_preferences`, separate from
  event timestamps. Grammar evidence remains in `skill_evidence`; flashcard
  reviews never write it.

New coverage in this task:

- two learners can store identical content and even the same `source_id`
  without cross-dedupe; each reads only their own note;
- an edit to a draft or an approved note preserves the note id, card id and
  `source_id`;
- a synthetic trigger rejects the event append, and the failed transaction
  leaves the card snapshot byte-identical with no event; retrying the same
  submission id after the trigger is removed applies exactly one transition;
- owner A cannot create, read, edit or reject owner B's draft or guess a
  foreign note/card id.

## T022b — retries and stale sessions

The review submission is keyed by `(owner_id, submission_id)`. An identical
retry returns the stored result with `duplicate: true` and performs no second
state transition or event insert. Reusing the same id with a different card,
revision or rating fails `IDEMPOTENCY_CONFLICT`. A fresh id against an old
revision fails `STALE_REVIEW` before scheduling.

The review API maps `STALE_REVIEW` to HTTP 409 with the learner-visible message
"This card changed in another tab. Reload to see the current version before
rating it again." A two-tab test asserts the conflict and the reload message,
and the concurrent-submission test proves exactly one of two writers wins.

Pending and rejected notes are never due and cannot be reviewed
(`NOT_APPROVED`); suspended cards cannot be reviewed (`SUSPENDED`). A foreign
card id reads as `NOT_FOUND`. Review submission does not touch grammar mastery
or `skill_evidence`.
