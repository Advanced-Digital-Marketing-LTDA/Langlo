## T010b implementation (2026-10-14 session, early)

Branch `codex/t010b-langlo-29` from the T010a base. Scope: sessions and recovery against disposable fixtures only — no live provider, no real accounts, no push.

### Red observations recorded

- `tests/auth.test.ts` written behavior-first: first run 13/14 pass; the single failure was an over-strict test assertion (expected `rate_limits.count >= 6`), not a framework gap — Better Auth saturates the counter at the configured `max` for rejected requests. Assertion corrected to `>= 5`.
- `tests/db-migrations.test.ts` after adding auth tables: 5 failures — (a) `matches every Drizzle table export` iterated `relations` exports as tables (fixed by filtering to table exports); (b) `Cannot add a column with non-constant default` on `ALTER TABLE users ADD updated_at DEFAULT (unixepoch()*1000)` — legal only while the table is empty, so the populated-schema upgrade path failed (fixed: constant `DEFAULT 0`; the framework always writes timestamps explicitly); (c) stale `__drizzle_migrations` count assertion 5→6.
- `tests/config.test.ts`: 3 failures — data-enabled configs must now also supply `BETTER_AUTH_SECRET` (auth is mandatory whenever data is enabled); tests updated to pass a synthetic secret.
- `tests/e2e/auth.spec.ts` debugging trail: form POSTs initially 403 (SvelteKit CSRF — needed `Origin` and `x-forwarded-proto` headers matching the adapter's `PROTOCOL_HEADER`); `Secure` attribute wrongly re-added by `applyAuthCookies` (SvelteKit `cookies.set` defaults `secure: true`; fixed by explicit `secure: false` mirroring source attributes); session rejected after login (double percent-encoding of the signed cookie value — `%3D` → `%253D`; fixed by decoding before `cookies.set`); sign-up endpoint returned 403 not 400 (Better Auth's own origin check needs an `Origin` header like a real browser). A stale server process holding port 4199 produced misleading results during debugging; the spec now binds a dynamically selected free port.

### Observed Better Auth 1.7.7 behavior (verified, not assumed)

- `POST /api/auth/sign-up/email` → `400 EMAIL_PASSWORD_SIGN_UP_DISABLED`; no user/account rows created.
- Sign-in: `401 INVALID_EMAIL_OR_PASSWORD` for unknown email and wrong password alike; `200` + database session row + cookie on success.
- Cookie attributes: `Max-Age=604800; Path=/; HttpOnly; SameSite=Lax`; `Secure` only when the configured origin is HTTPS (`useSecureCookies` pinned to origin scheme, not NODE_ENV).
- Reset request: identical success response for known and unknown email; delivery fire-and-forget; exactly one captured mail for the known address.
- Reset tokens: `verifications.identifier` stores a hash of `reset-password:<token>`; `value` holds the user id; raw token never persisted.
- Redemption: one success; replay → `400 INVALID_TOKEN`; concurrent barrier → exactly one `200`, one `400`.
- `revokeSessionsOnPasswordReset`: session rows for the account drop to 0 on redemption.
- Rate limits: `rate_limits` rows persist in SQLite across process restarts; sign-in returns `429` after 5 attempts/300s; request-password-reset `429` after 3/600s; rejected requests do not inflate the counter.
- Session tokens are stored **unhashed** in `sessions.token` (cookie appends a signature suffix). Acknowledged framework residual; compensating control is database-at-rest confidentiality. T010c re-asserts.
- Password hashing: framework scrypt via `ctx.password.hash` — used by the operator provisioning path through `internalAdapter` + `linkAccount` (provider `credential`, `emailVerified: true`).
