# Native flashcards architecture

**Status:** T003 feasibility architecture, 2026-10-10. This is a bounded design for later product tasks; the spike below is not production activation.

## Learner-owned content and identity

Langlo owns each learner's decks, tags, notes, generated cards, scheduling state, and append-only review history. Every persisted row has an owner relationship enforced in the database. Notes and decks receive stable IDs when created; generated card IDs derive from their persistent note ID and ordinal. IDs do not depend on editable text, deck names, or timestamps. A note can have Basic fields (`front`, `back`) or Cloze text. Generated mistake-card suggestions remain drafts until the learner approves them. A draft has a stable card ID but no scheduler row; approval atomically creates its initial scheduler state and makes it studyable. Rejecting an unapproved draft leaves no card state. The current application flow supports confirmed-mistake drafts, editable Basic/Cloze notes, approval and rejection, tags, search, suspension, review, and one-way export; these are implemented locally rather than future T021/T034 work.

T003 exercises one generated card per note. Basic content is an exact `{front, back}` object; restricted Cloze content is an exact `{text}` object. Each complete text field must be nonblank and at most 4,096 Unicode code points, enforced by the service and database, including direct SQL writes with leading or trailing whitespace. Note source IDs use the persistent `langlo:v1:` plus 64 lowercase hexadecimal characters format produced by `createSourceId()`, enforced by the service and database. Its Cloze validator accepts one cloze group (`c1`, including multiple `c1` spans) and rejects `c2` and other numbered groups. This narrow feasibility subset does not define eventual product Cloze scope or prove all Anki Cloze syntax.

## Study and scheduling

Browser study reveals the answer and records Again, Hard, Good, or Easy. The application presents due queues and progress from server-persisted card state so a learner can continue in another authenticated browser/device. The server owns scheduling decisions; a client submits a rating, UUID submission ID, and expected card revision. Scheduler version and parameters are stored with card state and review events, and each new event keeps the complete resulting scheduler snapshot. Older events may have no snapshot. Grammar mastery remains based on grammar exercise evidence; flashcard recall is a separate signal and must not silently change grammar mastery.

The current application uses `ts-fsrs@5.4.2` (MIT) as the actual scheduler. Its reviewed package source declares Node `>=20`, compatible with Langlo's Node 24.19.0 runtime. Version 5.4.2 is the source pin; it is maintained by Open Spaced Repetition and exposes the FSRS scheduling API used here. Current application defaults set 90% retention, `1m`/`10m` new-card steps and `10m` relearning; per-learner settings can change retention, new-card and relearning presets. Owner policy is to keep FSRS fuzz enabled (`enable_fuzz: true`): this seeded interval adjustment, currently seeded by card ID, spreads due dates. It affects schedules for new cards and future ratings of existing cards; it does not bulk-rewrite due dates already stored. Reviews apply the learner’s schedule to the stored scheduler parameters and record the effective parameters and resulting state in the event; unsupported versions or malformed persisted state are rejected without changing the card. This records the owner decision, not a claim of deployed production acceptance. [Pinned release](https://github.com/open-spaced-repetition/ts-fsrs/releases/tag/v5.4.2) · [package metadata and license](https://github.com/open-spaced-repetition/ts-fsrs/blob/v5.4.2/packages/fsrs/package.json) · [API](https://github.com/open-spaced-repetition/ts-fsrs/blob/v5.4.2/packages/fsrs/README.md).

## Writes, ownership, and recovery

Review submission updates scheduling state and appends one event in the same database transaction. `(owner, normalized UUID)` is the idempotency key: an identical retry returns the stored result; reuse with different input fails. The card revision is compared before scheduling, and a stale concurrent submission is rejected. Owner-scoped queries and composite foreign keys prevent another learner from reading or changing the note/card. Review history rejects application updates, direct deletes, and replacement inserts for an existing event key. Deleting an owning card, note, deck, or account intentionally cascades to its review events so the learner can erase their flashcard data; this is a full resource erasure, not an edit to retained review history. The database trigger allows the cascade only after the parent card has been removed. History is not a substitute for backups: recovery must restore a consistent database backup, preserve non-erased events, then verify derived card state against that log before service resumes. This recovery procedure is a design requirement, not exercised by this spike.

The T003 tests use synthetic learner identities against disposable file-backed SQLite/libSQL databases. Current route handlers map the verified auth session to the learner service context, but fixture tests alone do not prove production login, authorization deployment or production data access.

## Time and due-day policy

Review instants are stored in UTC. Study-day boundaries use the learner's saved IANA timezone (UTC when unset), not the device/browser timezone, with a 04:00 local cutoff. T003 recorded that the cutoff was undecided at that time; the later owner-approved saved-zone/UTC-fallback policy is captured in [domain context](../CONTEXT.md) and [route policy](routes.md). The implementation resolves daylight-saving gaps and repeated times to a concrete boundary. This source behavior does not establish production acceptance.

## Anki export surfaces

The current learner route `/app/decks/[id]/export` emits approved notes as private tab-separated text, with the persistent source ID in its GUID column; it omits scheduler state, due dates and review history. T003's synthetic `.apkg` candidates are generated by a separate feasibility script, not this route. Neither surface provides bidirectional sync. For the historical T003 `.apkg` artifacts, persistent Langlo source identities derive deterministic Anki note GUIDs, and deck/model IDs derive from stable source keys; changing note fields keeps the GUID, while renaming a deck changes its display name without changing identity. T003 uses feasibility-only `genanki==0.13.1` (MIT; Python `>=3.8`), whose source exposes GUID overrides, Basic/Cloze models, and `.apkg` generation. PyPI records its 2023-11-12 release; the upstream repository source inspected for this task has its latest commit at 2024-12-30. That maintenance cadence is a reason not to make it a permanent production runtime choice without a later review. [Pinned PyPI release](https://pypi.org/project/genanki/0.13.1/) · [source packaging/version metadata](https://github.com/kerrickstaley/genanki/blob/main/setup.py) · [note GUID implementation](https://github.com/kerrickstaley/genanki/blob/main/genanki/note.py) · [package generation](https://github.com/kerrickstaley/genanki/blob/main/genanki/package.py).

The historical T003 synthetic `.apkg` packages transfer note fields, note type/model identity, deck identity/name and tags; the current text export does not include tags. It must not claim to transfer Langlo due dates, FSRS state/parameters, or native review history. It does not import Anki review history back into Langlo. No two-way sync is promised. The license review found the pinned `ts-fsrs` and `genanki` releases MIT-compatible with the repository's selected PolyForm Shield 1.0.0 decision; no Anki code is copied. T001 selected PolyForm Shield 1.0.0 and implemented it in `LICENSE` and `COMMERCIAL.md`; remote publication remains pending.

For T003 `.apkg` client acceptance, import a generated synthetic package with Anki's **Import any learning progress** option left unchecked. The current Anki manual describes package import as adding or updating notes; it does not constitute evidence that this generated package updates content, avoids duplicates, or preserves an existing collection's review history under the chosen settings. Those behaviors remain unverified until the manual disposable-profile checklist in [T003 evidence](evidence/T003.md) is completed. [Anki manual: packaged deck import](https://docs.ankiweb.net/importing/packaged-decks.html) · [Anki manual: export](https://docs.ankiweb.net/exporting.html).

## Scope boundaries

T003 proves a small native persistence/scheduling path and creates synthetic `.apkg` candidates. Current application code additionally provides authenticated routes for deck/note management and review, per-learner schedule controls, grammar retention, saved-timezone study days, and one-way text export. Fixture coverage does not establish production auth or database acceptance. The current boundary does not include two-way Anki sync, AnkiWeb/API delivery, a Windows connector or self-hosted Anki sync.

T033–T037 are historical T003 follow-on labels, not a statement that the corresponding local service or route code is absent. Current behavior is described above. The manual disposable-profile acceptance for T003-generated `.apkg` files remains pending and is not replaced by archive checks; T024's broader real-client import/re-export and Anki-local review-history acceptance also remains open.
