# Native flashcards architecture

**Status:** T003 feasibility architecture, 2026-10-10. This is a bounded design for later product tasks; the spike below is not production activation.

## Learner-owned content and identity

Langlo owns each learner's decks, tags, notes, generated cards, scheduling state, and append-only review history. Every persisted row has an owner relationship enforced in the database. Notes and decks receive stable IDs when created; generated card IDs derive from their persistent note ID and ordinal. IDs do not depend on editable text, deck names, or timestamps. A note can have Basic fields (`front`, `back`) or Cloze text. Generated mistake-card suggestions remain drafts until the learner approves them. T021 adds draft generation from a confirmed practice mistake plus edit, approve and reject for those notes; broader create/edit/search/suspend/tag-management flows remain future product work.

T003 exercises one generated card per note. Basic content is an exact `{front, back}` object; restricted Cloze content is an exact `{text}` object. Each complete text field must be nonblank and at most 4,096 Unicode code points, enforced by the service and database, including direct SQL writes with leading or trailing whitespace. Note source IDs use the persistent `langlo:v1:` plus 64 lowercase hexadecimal characters format produced by `createSourceId()`, enforced by the service and database. Its Cloze validator accepts one cloze group (`c1`, including multiple `c1` spans) and rejects `c2` and other numbered groups. This narrow feasibility subset does not define eventual product Cloze scope or prove all Anki Cloze syntax.

## Study and scheduling

Browser study reveals the answer and records Again, Hard, Good, or Easy. The product should present due queues and progress from server-persisted card state so a learner can continue in another authenticated browser/device. The server owns scheduling decisions; a client submits a rating, stable submission ID, and expected card revision. Scheduler version and parameters are stored with card state and review events. Grammar mastery remains based on grammar exercise evidence; flashcard recall is a separate signal and must not silently change grammar mastery.

The feasibility implementation uses `ts-fsrs@5.4.2` (MIT) as the actual scheduler. Its reviewed package source declares Node `>=20`, compatible with Langlo's Node 24.19.0 runtime. Version 5.4.2 is the source pin; it is maintained by Open Spaced Repetition and exposes the FSRS scheduling API used here. New cards persist the library defaults: request retention `0.9`, maximum interval `36500` days, 21 default weights `[0.212, 1.2931, 2.3065, 8.2956, 6.4133, 0.8334, 3.0194, 0.001, 1.8722, 0.1666, 0.796, 1.4835, 0.0614, 0.2629, 1.6483, 0.6014, 1.8729, 0.5425, 0.0912, 0.0658, 0.1542]`, fuzz disabled, short-term scheduling enabled, learning steps `1m`/`10m`, and relearning step `10m`. Every review uses the parameters stored with its card and records that configuration with the event. Unsupported scheduler versions or malformed persisted parameters are rejected without changing the card. The package default without fuzz makes this spike reproducible; whether production should keep fuzz disabled is a T033 decision, not an owner-approved production setting. This dependency and its parameters remain an implementation choice to validate in later scheduling work, not settled production policy. ## Writes, ownership, and recovery

Review submission updates scheduling state and appends one event in the same database transaction. `(owner, submission ID)` is the idempotency key: an identical retry returns the stored result; reuse with different input fails. The card revision is compared before scheduling, and a stale concurrent submission is rejected. Owner-scoped queries and composite foreign keys prevent another learner from reading or changing the note/card. Review history rejects application updates, direct deletes, and replacement inserts for an existing event key. Deleting an owning card, note, deck, or account intentionally cascades to its review events so the learner can erase their flashcard data; this is a full resource erasure, not an edit to retained review history. The database trigger allows the cascade only after the parent card has been removed. History is not a substitute for backups: recovery must restore a consistent database backup, preserve non-erased events, then verify derived card state against that log before service resumes. This recovery procedure is a design requirement, not exercised by this spike.

The test session is a synthetic identity context injected by tests against disposable file-backed SQLite/libSQL databases. It is not the production authentication boundary and does not prove production login, authorization middleware, or authenticated browser sessions.

## Time and due-day policy

Store review instants as UTC timestamps and retain the learner's IANA timezone separately from device/browser timezone. Day-based queue boundaries must be calculated using the learner's current configured zone, including daylight-saving transitions and timezone changes. A 04:00 local cutoff is only a proposed configurable default for implementation evaluation; no product requirement or owner decision has approved that time. T036 must define behavior for zone changes, missed cutoffs, DST gaps/folds, and existing due items before production scheduling.

## One-way Anki package export

Anki is an optional one-way export target. Use persistent Langlo source identities to derive deterministic Anki note GUIDs. Derive deck and note-model IDs from stable source keys; changing note fields keeps the GUID, and renaming a deck changes its display name while retaining its identity. T003 uses feasibility-only `genanki==0.13.1` (MIT; Python `>=3.8`), whose source exposes GUID overrides, Basic/Cloze models, and `.apkg` generation. PyPI records its 2023-11-12 release; the upstream repository source inspected for this task has its latest commit at 2024-12-30. That maintenance cadence is a reason not to make it a permanent production runtime choice without a later review. [Pinned PyPI release](https://pypi.org/project/genanki/0.13.1/) · [source packaging/version metadata](https://github.com/kerrickstaley/genanki/blob/main/setup.py) · [note GUID implementation](https://github.com/kerrickstaley/genanki/blob/main/genanki/note.py) · [package generation](https://github.com/kerrickstaley/genanki/blob/main/genanki/package.py).

The package transfers note fields, note type/model identity, deck identity/name, and tags. It must not claim to transfer Langlo due dates, FSRS state/parameters, or native review history. It does not import Anki review history back into Langlo. No two-way sync is promised. The license review found the pinned `ts-fsrs` and `genanki` releases MIT-compatible with the repository's selected PolyForm Shield 1.0.0 decision; no Anki code is copied. The repository's license-file implementation remains pending under T001.

For client acceptance, import the package with Anki's **Import any learning progress** option left unchecked. The current Anki manual describes package import as adding or updating notes; it does not constitute evidence that this generated package updates content, avoids duplicates, or preserves an existing collection's review history under the chosen settings. Those behaviors remain unverified until the manual disposable-profile checklist in [T003 evidence](evidence/T003.md) is completed. [Anki manual: packaged deck import](https://docs.ankiweb.net/importing/packaged-decks.html) · [Anki manual: export](https://docs.ankiweb.net/exporting.html).

## Scope boundaries

This spike proves a small native persistence/scheduling path and creates importable package candidates. It does not activate production card management, production authentication, timezone behavior, offline-first study, native mobile applications, hosted per-user Anki, AnkiWeb API delivery, Windows connector delivery, or self-hosted Anki sync. Those are outside T003's revised core architecture.

The current follow-on split is T033 (full FSRS integration), T034 (deck/card management and the eventual Cloze contract), T035 (browser queue and study flow), T036 (account-timezone day boundaries), and T037 (one-way package export). T034's selected Cloze behavior depends on real-client import/re-import evidence. T024 owns broader cross-version import and Anki-local review-history retention acceptance. T003's manual client gate remains pending and is not replaced by its archive checks.
