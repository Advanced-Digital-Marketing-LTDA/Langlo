# Disposable data foundation

## Scope and authority

T009 implements the local SQLite/libSQL shape for the Langlo implementation plan's R001/R003/R009/R010. It is not production storage, authentication, a curriculum importer, scoring, a queue worker or Windows Anki integration. Database/ORM code is server-only. The only connection entry point is an explicitly marked disposable fixture, using `@libsql/client/sqlite3`; it cannot contact Turso or another network service.

The shared curriculum model covers French A1, German A1/A2 and English A1/A2. Metadata rows are not authored lessons or audited coverage. `users` now also carries the maintained-auth identity fields (email, email_verified, name, image, updated_at) added by migration 0005 per the contract in [docs/auth.md](auth.md); `email` stays nullable and unique so provisioned identities are unique while synthetic fixture users cannot collide on a blank value.

## Tables and data classifications

Identifiers are non-null text primary keys unless noted. Creation timestamps are non-null integer Unix milliseconds with a database default, currently unixepoch() * 1000. This has whole-second resolution and is not a unique ordering key. Future services must define an explicit tie-breaker rather than rely on timestamp uniqueness. Version strings identify the exact evaluator/rubric/scoring policy used; they are not mutable "current version" pointers.

## Relation and idempotency guarantees

Every private row carries `owner_id` referencing `users`. Composite parent keys bind related private IDs to that same owner and language. An enrollment belonging to B cannot be attached to A's session; A's session cannot receive B's attempt; a question cannot be substituted from another content version; an evaluation/evidence row cannot refer to someone else's attempt. `PRAGMA foreign_keys = ON` is applied on every fixture connection. These constraints complement, and do not replace, verified session-derived query filters in T011.

Submission identity is unique on `(owner_id, submission_key)`. Independent attempts and assisted retries are explicit records. Re-evaluation is intended to use a new evaluator/rubric version rather than silently replace prior history. Evaluation rows are not currently protected against direct UPDATE or DELETE; append-only behavior must be implemented and tested by T017/T018. Those tasks must also implement first-attempt eligibility, uncertainty rules and mastery decisions; the presence of a schema does not prove those features.

Canonical card identity is `(owner_id, language, skill_id, canonical_mistake)`, with a second globally unique `source_id`. `createSourceId` hashes a JSON-framed ordered tuple with SHA-256, producing `langlo:v1:<64 lowercase hex digits>`. It does not include editable fields, card format, question/content revision, profile, deck, timestamps or retry count. Input fields must be nonblank, NUL-free strings of at most 4,096 UTF-16 code units. Defining the canonical mistake is T021's responsibility; the hash does not perform normalization.

Hand-authored triggers make both the canonical card tuple/SourceID and persisted delivery id/owner/card/language/SourceID immutable. A deliberate new canonical mistake needs a new card identity. `deliveries` has one row per card and SourceID, with a composite foreign key including owner/language/source. Independent-process inserts released at a shared barrier converge on one identity, as verified by the retained concurrency test. Delivery retries update the same record; they cannot create another identity. Claimed rows require a complete nonempty token and increasing lease interval. Delivered rows require a note ID and delivery time; other states require null acknowledgement fields. This records acknowledgement shape, not proof that Anki confirmed it.

An insert-time approval trigger rejects delivery for a draft/rejected card; claimed/delivered updates also require approval. Strict version triggers enforce positive safe SQLite integers, and delivery counters/lease/ack timestamps enforce integer storage. Approval transitions, atomic claims, profile verification, retry/reconciliation behavior and edits to delivered notes remain T021–T024. Do not mistake this table for a functioning delivery queue.

## Versioned migration contract

- `0000_initial_study.sql` creates the ten shared/owned study tables and their constraints
- `0001_card_delivery_identity.sql` additively creates card/delivery tables, indexes and the two identity/approval triggers
- `0002_harden_persisted_invariants.sql` adds immutable delivery identity and strict numeric insert/update guards after validating existing numeric rows
- `0003_review_invariants.sql` validates existing rows, then adds supported enrollment-pair and nonblank/NUL-free SourceID identity-text guards
- `0005_auth_contract.sql` additively adds the four maintained-auth tables (`sessions`, `accounts`, `verifications`, `rate_limits`), auth columns on `users`, and their indexes/foreign keys. `users.updated_at` uses a constant `DEFAULT 0` because SQLite rejects non-constant `ALTER TABLE ADD COLUMN` defaults on populated tables; the framework always writes the timestamp explicitly
- `drizzle/meta` contains six generated SQLite snapshots and the six-entry journal; trigger-only migration 0003 does not rebuild tables and additive 0005 leaves all hand-authored triggers untouched. Runtime migration uses Drizzle's libSQL migrator and `__drizzle_migrations`
- Clean migration and repeated migration are tested against actual file-backed libSQL. The supported initial-to-current upgrade fixture contains two owners, two content versions, question/session metadata, an owned independent attempt and its evaluation. Their full before/after rows remain identical
- Generation reads `src/lib/server/db/drizzle.config.ts`, which has no connection credentials and no ambient environment import. `drizzle-kit check` validates migration metadata

The trigger SQL is deliberately hand-authored because Drizzle snapshots do not model triggers. Future table-rebuild migrations must preserve/recreate these triggers explicitly and test them. Once adopted outside disposable fixtures, applied migration files are immutable; add a new version instead of editing history. No down migration or automatic production rollback is provided. Code rollback and supported data restore remain separate; Turso provisioning/PITR/recovery are unverified release gates.

## Guarded fixture commands

Use Node 24 from the repository root. `node tests/fixtures/cli.ts init` returns JSON containing a new fixture root and database URL. Preserve those exact returned values for the following commands:

```sh
node tests/fixtures/cli.ts migrate --fixture-root "$FIXTURE_ROOT" --database-url "$FIXTURE_URL"
node tests/fixtures/cli.ts seed --fixture-root "$FIXTURE_ROOT" --database-url "$FIXTURE_URL"
node tests/fixtures/cli.ts reset --fixture-root "$FIXTURE_ROOT" --database-url "$FIXTURE_URL"
node tests/fixtures/cli.ts dispose --fixture-root "$FIXTURE_ROOT" --database-url "$FIXTURE_URL"
```

The fixture root must be a canonical absolute direct child of the system temporary directory named `langlo-fixture-*`, owned by the running user with no group/other access. It must contain the expected regular single-link marker file. Only the exact canonical `file:` URL for `test.sqlite` directly in that root is accepted. Network schemes, in-memory URLs, file authorities, query/fragment, alternate names/encodings, traversal, symlinked roots/files/markers/sidecars and hard-linked files are rejected before opening/resetting. The sqlite3-only client adds a second network prohibition.

Reset only removes `test.sqlite` and its known SQLite sidecars after validating every one. It leaves other files intact and never recursively deletes a directory. Dispose also refuses unknown files before removing the marker and empty root. Close all database clients before reset/dispose. These checks protect static path/link mistakes; they are not a filesystem sandbox against an adversary with the same OS identity racing path replacement. The private root excludes other OS users.

No command reads `DATABASE_URL`, `TURSO_DATABASE_URL`, tokens or production configuration. Seed data uses synthetic IDs and simple French metadata; it contains no real learner data or full curriculum. Repeated seed is idempotent. Invalid commands return exit 1 with a fixed safe error, omitting supplied targets and wrapped parameters.

## Review hardening evidence

The four-migration schema now closes the demonstrated delivery retargeting and non-integral version gaps. Regression tests were observed failing on the earlier schema and passing with migration 0002. Future table rebuilds must retain all hand-authored triggers. Invalid numeric rows in the supported older schema cause the additive upgrade to fail closed; no data is silently coerced. Full service authorization, approval/lease transitions and real provider operation are still separate tasks.
