# Disposable data foundation

## LANGLO-44–47 additions

Migration `0013_assessment_feedback` adds a nullable versioned question-plan JSON
to study sessions and a false-by-default `not_sure` flag to attempts. Completion
is derived from all planned questions being answered in the final write
transaction. Original attempts/evaluations and existing triggers are preserved.

Migration `0014_content_reports` adds owner-scoped report records, a unique
owner/submission key, a daily-count index, composite version/skill/language and
optional question foreign keys, allowlisted categories and bounded plain-text
comments. A null question reports the version's lesson. Reports never alter
content or learner evidence. The service checks enrollment and current/pinned
history before writing. Only disposable fixture migrations were exercised.

The existing `skill_evidence` table records the first qualifying evaluation for
each attempt/policy version; current mastery is recomputed from trusted source
history. Do not sum historical ledger contributions as current mastery. See
`docs/scoring-policy.md` and `docs/content-maintenance.md` for the policy and
correction/version-retention contract.

## Scope and authority

T009 records the original local SQLite/libSQL shape for the Langlo implementation plan's R001/R003/R009/R010 and its fixture-only connection path. That path accepts an explicitly marked disposable target and uses `@libsql/client/sqlite3`, so it cannot contact Turso or another network service. The current application runtime has a separate `openAppDatabase(RuntimeConfig)` seam: development/test use configured local data, while production configuration may select remote libSQL with `TURSO_AUTH_TOKEN_2`. This source capability is not evidence of a provisioned or live production database. Database/ORM code remains server-only; authentication, curriculum import, study/scoring, reports, Library and native flashcard services now exist, but their presence does not establish production or provider acceptance.

The shared curriculum model covers French A1, German A1/A2, English A1/A2 and, from migration 0026, Portuguese (Brazil) B1/B2. Metadata rows are not authored lessons or audited coverage. `users` now also carries the maintained-auth identity fields (email, email_verified, name, image, updated_at) added by migration 0005 per the contract in [docs/auth.md](auth.md); `email` stays nullable and unique so provisioned identities are unique while synthetic fixture users cannot collide on a blank value.

## Tables and data classifications

This table is a selected data-classification summary, not a full column inventory; the checked-in Drizzle schema and migration journal are authoritative for additional retention, native-flashcard, report and Library tables.

Identifiers are non-null text primary keys unless noted. Creation timestamps are non-null integer Unix milliseconds with a database default, currently unixepoch() * 1000. This has whole-second resolution and is not a unique ordering key. Future services must define an explicit tie-breaker rather than rely on timestamp uniqueness. Version strings identify the exact evaluator/rubric/scoring policy used; they are not mutable "current version" pointers.

Native flashcard notes are owner-scoped and editable. Drafts have a stable

initial `native_flashcards` row in the same transaction as the status change.

This account-lifetime model is a local schema decision consistent with the draft plan. It does not establish provider backup retention, notices, export/deletion workflows or legal compliance. Delivered Windows notes are outside this database. Content reports, TypeSafe usage and Library AI usage have current service consumers; see [content maintenance](content-maintenance.md) and [Library services](library-services.md).

## Relation and idempotency guarantees

Learner-owned application data rows are scoped either directly by `owner_id` referencing `users` or through an owner-bound parent, as with `library_document_files`. User identity and Better Auth records use their auth-model keys (such as `user_id`) rather than a universal `owner_id`; shared curriculum records and the global monthly `ai_usage` counter use their own keys and are not learner-owned, while `library_ai_usage` is owner-scoped by `(day, owner_id)` and cascades with the owner. Composite parent keys bind related learner-owned IDs to that same owner and language. An enrollment belonging to B cannot be attached to A's session; A's session cannot receive B's attempt; a question cannot be substituted from another content version; an evaluation/evidence row cannot refer to someone else's attempt. `PRAGMA foreign_keys = ON` is applied on every fixture connection. These constraints complement, and do not replace, verified session-derived query filters in T011.

Submission identity is unique on `(owner_id, submission_key)`. Independent attempts and assisted retries are explicit records. Re-evaluation is intended to use a new evaluator/rubric version rather than silently replace prior history. Evaluation rows are not protected against direct UPDATE or DELETE by the schema. Application code writes versioned evaluations and recomputes qualifying current evidence, but the table is not a database-enforced append-only ledger.

Canonical card identity is `(owner_id, language, skill_id, canonical_mistake)`, with a second globally unique `source_id`. `createSourceId` hashes a JSON-framed ordered tuple with SHA-256, producing `langlo:v1:<64 lowercase hex digits>`. It does not include editable fields, card format, question/content revision, profile, deck, timestamps or retry count. Input fields must be nonblank, NUL-free strings of at most 4,096 UTF-16 code units. The current mistake-card service uses `practice-mistake:<attemptId>` as the canonical input for a confirmed practice-error draft; the hash does not perform normalization.

Hand-authored triggers make both the canonical card tuple/SourceID and persisted delivery id/owner/card/language/SourceID immutable. A deliberate new canonical mistake needs a new card identity. `deliveries` has one row per card and SourceID, with a composite foreign key including owner/language/source. Independent-process inserts released at a shared barrier converge on one identity, as verified by the retained concurrency test. Delivery retries update the same record; they cannot create another identity. Claimed rows require a complete nonempty token and increasing lease interval. Delivered rows require a note ID and delivery time; other states require null acknowledgement fields. This records acknowledgement shape, not proof that Anki confirmed it.

An insert-time approval trigger rejects delivery for a draft/rejected card; claimed/delivered updates also require approval. Strict version triggers enforce positive safe SQLite integers, and delivery counters/lease/ack timestamps enforce integer storage. Approval transitions, atomic claims, profile verification, retry/reconciliation behavior and edits to delivered notes remain T021–T024. Do not mistake this table for a functioning delivery queue.

## Versioned migration contract — selected milestones

The bullets below highlight selected migrations; they are not a complete migration inventory.

- `0000_initial_study.sql` creates the ten shared/owned study tables and their constraints
- `0001_card_delivery_identity.sql` additively creates card/delivery tables, indexes and the two identity/approval triggers
- `0002_harden_persisted_invariants.sql` adds immutable delivery identity and strict numeric insert/update guards after validating existing numeric rows
- `0003_review_invariants.sql` validates existing rows, then adds supported enrollment-pair and nonblank/NUL-free SourceID identity-text guards
- `0005_auth_contract.sql` additively adds the four maintained-auth tables (`sessions`, `accounts`, `verifications`, `rate_limits`), auth columns on `users`, and their indexes/foreign keys. `users.updated_at` uses a constant `DEFAULT 0` because SQLite rejects non-constant `ALTER TABLE ADD COLUMN` defaults on populated tables; the framework always writes the timestamp explicitly
- `0006_content_version_ledger.sql` additively creates `curriculum_imports` (curriculum version primary key; the fingerprint must be 64 lowercase hex characters)
- `0007_content_payload_fingerprint.sql` adds nullable immutable-version payload fingerprints for verified legacy adoption
- `0010_lessons_and_pause.sql` additively creates `lessons` (one row per content version: title, explanation, examples and references as JSON, own fingerprint; a stored lesson is immutable, a version without one may gain it under a new curriculum version) and adds nullable `study_sessions.paused_at`. Nothing is rewritten
- `0011_one_independent_attempt.sql` additively creates the partial unique index `attempts_session_question_independent` on `(owner_id, study_session_id, question_id)` where `evidence_kind = 'independent'`. It fails loudly on a database that already holds two independent attempts for one session question; resolve those rows by hand before applying. Applying it to any database is a human action.
- `0009_question_payload.sql` additively adds nullable `questions.prompt`, `answer` and `alternatives` (JSON); existing rows stay null until a fingerprint-verified re-import backfills them
- `0008_question_holdouts.sql` additively adds `questions.holdout`, `NOT NULL DEFAULT false` with a 0/1 check; existing rows remain practice questions, with all learner history and triggers preserved
- `0016_content_updates.sql` additively adds nullable `questions.lineage_key` (identity of a question across lesson versions), nullable `skills.retired_at`, `replaced_by` and `carry_progress`, and the `content_changes` table (what each curriculum import changed: skills added or retired, versions added or quarantined, questions same, changed, new or removed). Nothing is rewritten; see [content-update.md](content-update.md)
- `0017_lesson_translations.sql` additively creates `lesson_translations` (one row per content version and explanation language, currently `pt`: title, explanation, examples and references as JSON, own fingerprint; immutable like `lessons`, and only importable beside the English lesson). A learner whose enrollment chooses `pt` gets the translation when one exists, otherwise the English lesson with an on-page notice. Nothing is rewritten.
- `0018_content_change_kinds.sql` rebuilds `content_changes` to allow the `lesson-translation-added` audit kind while preserving existing rows and indexes.
- `0019_bizarre_ink.sql` additively adds `native_flashcard_notes.explanation` (default empty), nullable `source_skill_id`, `source_content_version_id` and `source_attempt_id`, and the partial unique index `native_flashcard_notes_owner_source_attempt_unique` on `(owner_id, source_attempt_id)` where the attempt is not null. It creates no table and rewrites no row
- `0020_note_source_shape.sql` adds hand-authored INSERT and UPDATE triggers requiring the three `native_flashcard_notes` source columns to be all null or all set. This closes the direct-SQL gap left by SQLite's inability to add a CHECK to an existing table without a rebuild
- `0021_note_source_attempt.sql` adds INSERT and UPDATE triggers requiring a non-null source attempt to belong to the note owner and to match the stored skill and content version. The trigger checks the owner-bound `attempts` row, so direct SQL cannot forge provenance
- `0022_note_source_owner_update.sql` drops and recreates the provenance UPDATE trigger with `owner_id` and `deck_id` in its `UPDATE OF` list, so reassigning a sourced note revalidates it. `0021` remains byte-identical to its applied content (`sha256 bc38720f055d...`); this is a forward correction, not an edit to the applied migration
- `0026_portuguese_tracks.sql` widens the language and level CHECKs of `skills` and `enrollments` to `pt` and `B1`/`B2`. SQLite cannot alter a CHECK, so both tables are rebuilt with every row kept; a gate fails the migration if either row count changes. The 0003 triggers on both tables go with the rebuild and are recreated: the `enrollments` track guard now also allows pt B1/B2, new triggers refuse Portuguese explanations on the Portuguese track, and the two `skills` identity triggers are recreated unchanged. No other table is touched It also refuses to run when foreign keys are enforced (dropping `enrollments` would cascade into `study_sessions`); the libSQL `migrate` path turns enforcement off before its transaction, so only that runner may apply it.
- `drizzle/meta` contains 36 generated SQLite snapshots (none for trigger-only 0003, 0020, 0021 and 0022) and the 40-entry journal. Migration `0033_typesafe_ai_usage.sql` widens the `ai_usage` API check while copying existing counters, retaining historical `decisions` rows alongside `typesafe`. The repaired LANGLO-10 migration `0023_solid_dazzler.sql` adds nullable `state_json` to existing review events without dropping `WITHOUT ROWID` or the append-only review triggers. It preserves legacy review rows with null snapshots, removes only unreviewed draft/rejected scheduler rows, and fails closed if a draft has review history. Runtime migration uses Drizzle's libSQL migrator and `__drizzle_migrations`; the separate, opt-in `npm run db:remote-test` command (see [deployment/remote-test-migrations.md](deployment/remote-test-migrations.md)) uses the same ledger for the isolated remote test database and verifies every applied checksum
- Clean migration and repeated migration are tested against actual file-backed libSQL. The supported initial-to-current upgrade fixture contains two owners, two content versions, question/session metadata, an owned independent attempt and its evaluation. Their full before/after rows remain identical
- Generation reads `src/lib/server/db/drizzle.config.ts`, which has no connection credentials and no ambient environment import. `drizzle-kit check` validates migration metadata

The trigger SQL is deliberately hand-authored because Drizzle snapshots do not model triggers. Future table-rebuild migrations must preserve/recreate these triggers explicitly and test them. Once adopted outside disposable fixtures, applied migration files are immutable; add a new version instead of editing history. No down migration or automatic production rollback is provided. Code rollback and supported data restore remain separate; Turso provisioning/PITR/recovery are unverified release gates.

Migration `0037_light_drax.sql` adds owner-scoped `library_documents` with extracted text, source language, sentence count and resumable sentence position; account deletion cascades. Migration `0038_demonic_garia.sql` adds per-owner daily Library AI call counters, also deleted with the owner. Migration `0039_medical_maria_hill.sql` adds `library_document_files`, which keeps the uploaded PDF, DOCX or EPUB (up to 10 MB, owner-scoped through its document and deleted with it) so the reader can show the book itself, and adds `library_documents.progress_location`, the page or EPUB location where the reader stopped. TXT uploads keep only their extracted text.

## Guarded fixture commands

Use Node 24 from the repository root. `node tests/fixtures/cli.ts init` returns JSON containing a new fixture root and database URL. Preserve those exact returned values for the following commands:

```sh
node tests/fixtures/cli.ts migrate --fixture-root "$FIXTURE_ROOT" --database-url "$FIXTURE_URL"
node tests/fixtures/cli.ts seed --fixture-root "$FIXTURE_ROOT" --database-url "$FIXTURE_URL"
node tests/fixtures/cli.ts reset --fixture-root "$FIXTURE_ROOT" --database-url "$FIXTURE_URL"
node tests/fixtures/cli.ts dispose --fixture-root "$FIXTURE_ROOT" --database-url "$FIXTURE_URL"
```

The fixture root must be a canonical absolute direct child of the system temporary directory named `langlo-fixture-*`, owned by the running user with no group/other access. It must contain the expected regular single-link marker file. Only the exact canonical `file:` URL for `test.sqlite` directly in that root is accepted. Network schemes, in-memory URLs, file authorities, query/fragment, alternate names/encodings, traversal, symlinked roots/files/markers/sidecars and hard-linked files are rejected before opening/resetting. The sqlite3-only client adds a second network prohibition.

Reset only removes `test.sqlite` and its known SQLite sidecars after validating every one. It leaves other files intact and never recursively deletes a directory. Dispose also refuses unknown files before removing the marker and empty root. Close all database clients before reset/dispose. These checks protect static path/link mistakes; they are not a filesystem sandbox against an adversary with the same OS identity racing path replacement. The private root excludes other OS users.

These fixture commands do not read `DATABASE_URL`, `TURSO_DATABASE_URL`, tokens or production configuration. Seed data uses synthetic IDs and simple French metadata; it contains no real learner data or full curriculum. Repeated seed is idempotent. Invalid commands return exit 1 with a fixed safe error, omitting supplied targets and wrapped parameters.

## Historical T009 review-hardening evidence

T009's four-migration fixture schema closed the demonstrated delivery-retargeting and non-integral-version gaps; regression tests were observed failing on the earlier schema and passing after migration 0002. This is historical evidence about that T009 boundary, not a count or acceptance claim for the current schema. Future table rebuilds must retain all hand-authored triggers. Invalid numeric rows in supported older schemas cause the additive upgrade to fail closed; no data is silently coerced. Route-level and production-provider acceptance remain separate gates.
